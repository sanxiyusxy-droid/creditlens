## 启动（演示前 5 分钟准备）

```powershell
docker compose up -d                                          # PG/Qdrant/MinIO/Redis
powershell -ExecutionPolicy Bypass -File scripts\start_demo.ps1   # API + 演示页
# 浏览器打开 http://localhost:8501
```

若库为空：`uv run python scripts/run_evaluation.py` 会自动 seed（幂等，可重复执行）。

---

## 第 1 幕（2 分钟）：政策时点切换 —— "系统知道'当时'适用哪版政策"

Tab ①，同一个问题（"流动资金贷款对资产负债率的要求是多少？"）：

1. 点"以 2026-06-30 检索" → 命中 **v2026 政策：负债率 ≤ 70%、流动比率 ≥ 1.0**；
2. 点"以 2025-06-30 检索" → 命中 **v2024 政策：负债率 ≤ 65%、流动比率 ≥ 1.2**（不同 document_version_id）。

**讲解点**：这不是 prompt 里加了一句"注意时间"——是 `[valid_from, valid_to)`
硬过滤在**召回前**执行（Qdrant payload index must_not 范围过滤 + PG 回表复核双防线），
时点错误的版本根本不进入候选。评测集中 12 道版本时点题 Policy Version Accuracy = 100%。

## 第 2 幕（3 分钟）：完整预审 —— "Agent 只能说有证据的话"

Tab ②，点"🚀 启动完整预审"：

1. 返回 202 + run_id（异步，DAG 后台按阶段提交）；点"刷新状态"看状态推进：
   RECEIVED → AUTHORIZED → VALIDATING_CASE → PLANNING → EXECUTING →
   SYNTHESIZING → CHALLENGING → AUDITING → HUMAN_REVIEW；
2. Claims 表出现（约 9 条）：每条有 verdict / 正证据 / 反证据 / 计算数。

**讲解点**：
- Policy/Financial Agent 不直接对话，只交换结构化 AgentArtifact；
- statement 由 LLM 概括，但**证据绑定与 verdict 是确定性的**；LLM 输出若出现
  "批准/拒贷"类越权措辞会被输出边界强制降级（有故障注入测试锁定该行为）；
- Challenger 主动检索反证（如"欺诈""处罚"），正反证据都保留，不投票；
- Auditor 做三级确定性校验：Contract → 证据/版本/案件/Snapshot 回表 → 公式重放，
  缺 locator 或失效的正证据、反证据都 fail closed；它不使用 LLM 评 LLM，也不冒充
  Claim-Evidence 语义蕴含裁判。

## 第 3 幕（2 分钟）：证据回原文页 —— "每句话可以点回 PDF"

Tab ③，从检索候选选择证据 → "打开原文页" → 渲染原始 PDF 页；Tab ④ 的 Claim
表同屏展示 supporting/opposing locator，并可选择任一正证据或反证据预览原文。

**讲解点**：Evidence Locator 包含 section/version/parse_run/页码/text_hash；
服务端校验 Membership + 案件绑定 + 解析批次一致才渲染——同租户另一案件的
用户拿同样的 locator 会被拒（有跨案件越权测试）。文本哈希不一致返回
STALE_REFERENCE 而不是悄悄换内容。

## 第 4 幕（3 分钟）：HITL 与报告 —— "AI 不做授信决定"

Tab ④：

1. 显示 blocking Claims（Auditor 判 PENDING/打回的）；
2. 先只批准**一部分** → 状态保持 HUMAN_REVIEW（演示"部分批准不能完成"）；
3. 批准全部 → COMPLETED，报告版本出现（含 content_hash 与免责声明
   "不构成授信批准或拒绝决定"）。

**讲解点**：人工决定是追加写（不覆盖 Agent 输出）；报告持久化是 COMPLETED
前置条件；幂等键防重复提交；所有 blocking Claim 解决前 SUBMIT_REPORT 会被拒。

## 第 5 幕（1 分钟）：Trace —— "每一步都可回放"

Tab ⑤，加载状态审计：页面当前展示追加写、单调 `sequence_no` 的 `run_events`。v1.5
Invocation 明细已经由同一个 Trace API 返回，但当前 Streamlit 表仍只投影 `events`；演示新增
字段时可在另一个 PowerShell 窗口查看原始响应：

```powershell
$runId = "<页面中的 run_id>"
$trace = Invoke-RestMethod "http://localhost:8000/api/v1/runs/$runId/trace"
$trace.integrity
$trace.delivery
$trace.invocations | Select-Object invocation_id, kind, name, status, integrity, delivery
```

**讲解点**：`run_events` 是业务状态事件源，SSE 进度与状态回放从这里来；
`invocation_records` 是 Model/Tool 调用事实源，两者职责不同。v1.5 候选把 Grounded QA、
Policy 的已接线 structured Model 与 ToolGateway 四类终态写入独立短审计事务，
InvocationRecord 与 TelemetryOutbox 同事务提交。Trace 返回前复核 payload、Hash、列投影、
Outbox 与 Run 绑定；无效 payload 不回显。`MISSING` 表示合法 InvocationRecord 缺 Outbox，
`INVALID` 才表示 payload/Hash/projection/binding 损坏。

默认 Worker 是 disabled，因此未配置真实 Exporter 时看到 `delivery.status=PENDING` 是诚实
状态，不是故障，也不能说 `COMPLETE`。内置 Noop Exporter 只用于 local/test 验证失败路径，
它 fail closed 并最终使耗尽重试的行进入 `DEAD`，不能用来演示成功导出。

## 面试官可能追问 & 一句话回答

| 追问 | 回答要点 |
|---|---|
| 历史 Run 会漂移吗？ | Snapshot 冻结文档 ParseRun + 财务 Fact 集合；重放公式 trace_hash 不变（有测试） |
| 跨租户/跨案件？ | RLS（NOBYPASSRLS 业务角色）+ 服务端派生 ACL + 空 ACL 默认拒绝 + 跨案件测试 |
| 幻觉怎么防？ | Claim 必须绑定证据/计算，Auditor 哈希回表；LLM 只负责措辞，越界降级 |
| Reranker 挂了？ | 降级 RRF 顺序并记录 rerank_degraded，不假成功（故障注入测试） |
| 双库一致性？ | Transactional Outbox + 幂等 UUIDv5 Point + Activation Guard；v1.2.0 用 `SKIP LOCKED` 避免多 Worker 抢同批任务 |
| 为什么调用投递不是 exactly-once？ | Exporter 成功后、Worker 提交 DELIVERED 前仍可能崩溃并重投；系统提供 at-least-once + Invocation UUID 幂等键，消费端必须去重 |
| Trace 的 COMPLETE 代表什么？ | 只表示当前持久 Invocation 集合有效且 Outbox 均已 DELIVERED；不代表答案正确，也不能证明所有实际调用均已入账 |
| EMPTY 就是丢记录吗？ | 不一定；可能是合法零调用，也可能是提交前未入账。当前没有 expected-invocation set/reservation/count，无法区分 |
| 为什么默认不开 Telemetry Worker？ | 内置 Noop 会 fail closed；当前 Outbox UPDATE 仍由 API/内置 Worker 共用的 creditlens_app 持有，数据库不能区分二者，专用生产 Worker role 尚未实现 |
| 取消等待超时会终止 DB 事务吗？ | 不会；上限只约束调用方同步等待，shield 的底层事务仍可能稍后提交或失败，它不是 DB deadline |
| 指标属于哪版？ | 检索正式三轮属于评测源码 `9e64dbb`（`v1.2.0`）；答案第二轮属于 `c4289a1`（`v1.3.0`）。release tag 与报告源码 commit 分离 |

## v1.3.0 补充讲解（1–2 分钟）

Tab ① 已接入 Grounded QA。演示时强调四种状态而不是只展示一条“看起来合理”的答案：

1. `ANSWERED`：每条 Claim 有正式 citation，点击可回原文；
2. `ABSTAINED`：证据不足但系统正常运行，返回稳定 refusal reason code；
3. `NEEDS_REVIEW`：结构覆盖、极性或冲突信号触发人工复核，不展示 direct answer；
4. `TECHNICAL_FAILURE`：Schema、审计硬门禁或基础设施失败，不得伪装成业务拒答。

第二轮 41 题实测为 23/8/6/4；Citation-set P/R/F1 为 76.67%/69.70%/73.02%，
拒答理由匹配 8/11，技术失败率从首轮 17.07% 降至 9.76%。演示时必须补一句：这些是
合成集上的确定性词面、数值和引用集合指标，`semantic_entailment_evaluated=false`，
Citation F1 不是 Faithfulness；仍有 1 个审计失败和 3 个连续 Schema 失败待提升鲁棒性。

## v1.4.0 补充讲解（1–2 分钟）

不向模拟评审员打开正式 Source，只展示文档中的 Source Hash、Claim 数和 Evidence 数；
正式文件位于 `.gitignore` 排除的 `evaluation/semantic/private/`，和私有 mapping 一样由
评测管理员保管：

1. prediction、主 raw checkpoint、证据补全 checkpoint 三份输入均做字节级 Hash 绑定；
2. Source 有 41 Claim / 46 Evidence，来自 23 道 ANSWERED 和 6 道 NEEDS_REVIEW；
3. 管理员按操作协议用 CSPRNG 为两名评审员分配互不复用的 22–128 位 URL-safe 高熵伪名，
   分别生成不同随机顺序的 package/worksheet；代码只校验长度和字符集。两套 package 共用
   同一个显式 aware `generated-at`，配合固定 Source、
   各自私有伪名与 ordering seed 可逐字节复现，但演示不展示伪名。两名隔离真人不得访问
   Source、仓库 gold、私有 mapping、另一人的材料或模型，填完后各自通过显式 attestation
   编译 submission；
4. 两人不形成严格共识的 Claim（包括任一 `SKIP/CONFLICT`）才进入盲化 adjudication
   package/worksheet，由第三名隔离真人裁决为语义标签或 `EXCLUDE`，最后运行
   `score --require-complete`。裁决 package 也显式冻结不早于两份 review `submitted_at` 的
   独立 aware `generated-at`；公开包只
   含匿名 prior decision，不含 rationale、question/claim ID、评审身份或 gold，且仍只受控
   分发；所有 package/worksheet、私有 mapping、身份 roster 和原始 submission 均不进 Git；
5. attestation 是参与者的自我声明，不是技术证明。当前没有任何真人 label/submission 或
   adjudication，所以只能说“正式语义评测 Source 与执行工具链已就绪”，不能报 Semantic Entailment 或
   Faithfulness 分数；
6. 当前已私有生成两套各 41 项的 package + blank worksheet + mapping kit；readiness 只是
   INCOMPLETE、收到 0/82 rating 的诊断，不是正式报告/分数，不能引用零值 label rate。代码
   门禁验证两个不同 reviewer 伪名、82 个 rating，以及必要时一个不同 adjudicator 伪名完成
   裁决/`EXCLUDE`；不能证明三个伪名属于三个物理真人。真人隔离由私有 roster、隔离账号和
   人工监督保证。未来 final entailed rate 也只是 Claim 被所给 Evidence 语义支持的代理指标，
   不是答案正确率。

失败链路的演示口径：同一失败幂等请求会恢复稳定错误类型，而不是统一成
`PREVIOUS_IDEMPOTENT_REQUEST_FAILED`；终态事件若重复、不是最后一条、租户/案件不一致或
错误类型不在枚举中，就 fail closed。结构化模型输出失败只暴露安全 Schema 指纹/分类，
不把原始响应或 ValidationError message 写入 Trace。若调用被取消，取消信号继续向上传播，
这是 v1.4 的历史语义：`shield` 保护没有应用层 timeout 的 best-effort 清理；DB 可用时
Run 通常以
`QA_CALL_CANCELLED` 终结，重试同幂等键可获得稳定失败分类。若 DB 同时不可用，清理异常
不会覆盖原取消，但仍需 lease/reconciler 做崩溃收口。Tool 并发预算在执行前原子占位，
Run 级 ContextVar 防止并发 Event 串线。

## v1.5.0 候选补充讲解（1–2 分钟）

推荐按“事实、投递、复核、边界”四步讲：

1. **事实**：每个已接线 structured Model 和 Tool 终态先变成内容脱敏的
   `InvocationEnvelope v2`；Tool 输入输出保存实例密钥 HMAC 指纹，不保存原文。账本按
   Invocation UUID 幂等，同 UUID 不同 Hash 或父绑定 fail closed；
2. **投递**：`invocation_records` 与初始 `PENDING telemetry_outbox` 在同一个独立短事务
   提交。Worker 用 `SKIP LOCKED + lease + reclaim + backoff + max attempts + DEAD`。若
   Exporter 协程取消留下过期 `PROCESSING`，下一次扫描会回收；次数已经耗尽则直接转
   `DEAD`，不无限重试；
3. **复核**：Trace API 不直接相信 JSON，而是重建 Envelope 与公开投影，核对 Hash、关系
   列、Outbox 和 `review_runs` 的 tenant/case/run 绑定。汇总显示
   `PENDING/COMPLETE/DEGRADED/EMPTY`，历史未回填 Run 单独为 `LEGACY_UNAVAILABLE`。
   `MISSING` 是合法 record 缺 Outbox，`INVALID` 是 payload/hash/projection/binding 损坏；
   `COMPLETE` 只证明当前持久集合有效且均已投递，不能证明所有实际调用均已入账。`EMPTY`
   也无法在没有 expected-invocation set/reservation/count 时区分合法零调用和提交前丢失；
4. **边界**：这是 at-least-once，不是 exactly-once；没有 OTel/Prometheus/Dashboard 或历史
   回填；`generate_text` 自由文本路径未全覆盖；DB 提交前故障不能保证记录；取消 timeout
   只约束调用方等待，返回时尚不能确定最终是否入账，shield 的底层事务可能稍后提交/失败，
   并非 DB
   deadline；Telemetry lease 也不是业务 Run lease。Multi-Agent 的 heartbeat/reconciler 与
   持久队列留给后续版本。

权限层面补一句：`invocation_records` 对业务角色仅追加写；Outbox 不可改
tenant/case/run/topic，只开放投递生命周期列；`review_runs` 的租户、案件和 Snapshot 绑定
不可变。但 Outbox 生命周期列的 UPDATE 当前由 API 与内置 Worker 共用的
`creditlens_app` 持有，数据库不能区分更新者；专用生产 Worker role 尚未实现。正式部署前
必须拆出专用 service role 或按 tenant 分片的身份。

候选状态口径：当前可以说“实现与本地门禁已完成，等待 GitHub PR/main/tag 发布门禁”；
不能称 `v1.5.0` 已发布。完整说明见
`docs/v1.5_持久调用账本与遥测投递.md`。
