# CreditLens v1.4：受控语义评审与调用观测

> 状态：`v1.4.0` 本地发布候选，尚未推送、合并、运行 GitHub CI 或发布标签。
> 已发布版本仍为 `v1.3.0`。本文件只描述当前候选工作树中已验证的能力。

## 1. 本版解决什么问题

v1.3 已经把检索命中、引用集合、确定性词面/数值匹配和业务拒答分开评测，但仍有三个
工程缺口：失败幂等重放只返回泛化错误；Citation-set 一致不能证明 Claim 被证据语义
支持；完整预审中的 Tool 调用缺少统一、可查询的脱敏记录。v1.4 对应补齐：

1. **失败可解释重放**：新请求使用 `grounded_qa_request_v2`；失败 Run 只从唯一、最后、
   与租户/案件/状态转换一致的终态事件恢复固定错误枚举。v1.3 已完成 Run 仍可在旧 Hash
   与原始 `RUN_CREATED` 契约同时匹配时兼容重放；旧失败或疑似降级伪装一律拒绝。请求
   取消时不吞 `CancelledError`；DB 可用时 shield 有界失败收口，以 `QA_CALL_CANCELLED`
   终结 Run。若 DB 同时不可用，清理失败不覆盖原取消，但持久收口仍依赖未来的 lease/
   reconciler。
2. **受控人工语义蕴含协议**：从正式 prediction 与 gold-free raw checkpoint 构建
   Claim-Evidence Source，再为不同评审员生成独立随机顺序的评审包；评分阶段才使用私有
   映射聚合，不让生成阶段读取 gold，也不让同一个生成模型给自己打分。
3. **统一调用信封**：Model/Tool 共用只含身份、状态、时间、Hash、Token 和安全错误码的
   `InvocationEnvelope`。`FULL_REVIEW` 的 Tool 调用已写入现有 `run_events`，沿用 Run、
   tenant、case 和连续 sequence；模型侧仍由 Grounded QA 的既有事件路径写入，再通过
   legacy adapter 转换为统一信封。

## 2. 正式语义评测 Source

评测管理员私有的正式 Source 为：

`evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json`

它由三份精确输入字节构建：

| 输入角色 | SHA-256 |
|---|---|
| 正式 41 题 prediction | `3c2714e8bafb6d67b62034cb50d4123710efaf2da40519f8df4fcb8b4b6e59f2` |
| 主 raw checkpoint | `ac1fac81490867c269d30487ed9e703f1d2ed3af242f2c87773a4f4284c67e17` |
| 冻结证据补全 checkpoint | `51dd76603bf3b0390e5a87e72b3151b59836c9bd0aaf2f8e245abc8202ee7b06` |

Source 自身 SHA-256 为
`b77c6d8f4211fdfc6c940accb3c001b6f675dca0cbd9592a5c8e1e2756cfb5e5`，包含 **41 个
Claim / 46 条 supporting evidence**。来源是 23 个 `ANSWERED` 和 6 个 `NEEDS_REVIEW`
题目，共 29 题；8 个 `REFUSED` 与 4 个 `TECHNICAL_FAILURE` 没有可审查 Claim，不进入。

Source 不含问题正文、expected answer、gold label、answerable、citation gold、case key 或
reviewer 身份，但包含管理员聚合所需的 `question_id/claim_id`。因此它不能交给评审员，也
不能公开入 Git：若评审员同时访问 Source 与仓库 gold，可通过 ID 连接破坏盲法。每条
Evidence 以 `section_id + content_sha256` 绑定冻结正文，正文与 Hash
不一致、引用 ID 不能按 UUIDv5 重算、预测与 checkpoint 的 Run/Snapshot/Model Invocation
归因不一致时均 fail closed。

## 3. 受控评审执行步骤

### 3.1 如需重新构建 Source

```powershell
uv run python scripts/build_entailment_source.py `
  --prediction evaluation/predictions/answer_eval_v1_c4289a1_20260810T125041Z.json `
  --raw-checkpoint evaluation/predictions/answer_eval_v1_c4289a1_20260810T125041Z.json.raw.checkpoint.json `
  --evidence-checkpoint evaluation/predictions/answer_eval_v1_c9decbc_20260809T1442Z.json.raw.checkpoint.json `
  --source-id answer-eval-v1-c4289a1-semantic-source-v1 `
  --created-at 2026-08-12T14:33:02.696624Z `
  --output evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json
```

`--created-at` 必须带时区；固定该值可逐位复现上面的 Source SHA。省略时使用当前 UTC，适合
生成新的评审批次，但产物时间戳与文件 Hash 会相应变化。所有输入/输出路径会做底层文件
同一性检查，硬链接别名也会 fail closed；已存在输出默认不覆盖，必须显式传 `--overwrite`。

raw checkpoint 可能包含完整合成证据正文，Source 又含管理员解盲所需的 question/claim ID；
二者均由 `.gitignore` 排除。Git 只归档构建/校验代码、无真实映射的 Schema 模板，以及
Source 的 SHA、Claim/Evidence 数和输入 Hash 证明，不归档正式 Source 本体。`packages/`、
`submissions/`、`reports/` 和 `evaluation/semantic/*.json` 也默认忽略，避免操作者把评审
中间产物误写到公开路径后提交。

### 3.2 为两个评审员分别生成受控评审包

```powershell
uv run python scripts/build_entailment_review_package.py `
  --source evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json `
  --reviewer-id reviewer-a --ordering-seed sealed-study-a `
  --output evaluation/semantic/packages/reviewer-a.package.json `
  --mapping-output evaluation/semantic/private/reviewer-a.mapping.json

uv run python scripts/build_entailment_review_package.py `
  --source evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json `
  --reviewer-id reviewer-b --ordering-seed sealed-study-b `
  --output evaluation/semantic/packages/reviewer-b.package.json `
  --mapping-output evaluation/semantic/private/reviewer-b.mapping.json
```

只把 `packages/*.package.json` 交给对应评审员；Source、仓库 gold 和 `private/` 中的
question/claim 映射都不能在提交评分前向评审员开放。评审账号或分发环境必须与代码/数据
仓库隔离；否则仅靠随机排序不能形成有效的受控盲化。
评审标签为 `ENTAILED / CONTRADICTED / NOT_ENOUGH_INFO`；无法判断可标 `SKIP`，证据互相
冲突可标 `CONFLICT`，后二者必须写理由，且不冒充语义标签。

### 3.3 聚合评分

```powershell
uv run python scripts/score_entailment_review.py `
  --source evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json `
  --package evaluation/semantic/packages/reviewer-a.package.json `
  --mapping evaluation/semantic/private/reviewer-a.mapping.json `
  --submission evaluation/semantic/submissions/reviewer-a.submission.json `
  --package evaluation/semantic/packages/reviewer-b.package.json `
  --mapping evaluation/semantic/private/reviewer-b.mapping.json `
  --submission evaluation/semantic/submissions/reviewer-b.submission.json `
  --output evaluation/semantic/reports/entailment_report_v1.json
```

所有构建/评分 CLI 默认禁止覆盖，也拒绝 output 与任一 input 同路径或硬链接别名；只有
显式 `--overwrite` 才原子替换。报告包含微/宏标签率、覆盖率、冲突、裁决覆盖、pairwise
agreement 和满足条件时的 Cohen's κ。

**当前没有人工 submission，也没有正式语义分数。** Source 就绪不等于
`semantic_entailment_evaluated=true`；v1.3 的 Citation F1 仍不能称为 Faithfulness。

## 4. Invocation Envelope 与边界

统一信封支持：

- `MODEL / TOOL`、`SUCCESS / FAILED / DENIED / CANCELLED`；
- provider/model/tool/version、actor、task、aware 时间、monotonic latency；
- Prompt/Request/Response 指纹、Token、尝试次数与固定错误码；
- Tool 输入输出使用实例密钥 HMAC-SHA256 和带类型的规范化；不可规范化时只记录安全
  错误码，绝不把观测失败改成工具业务失败；
- 同一 task 的预算在工具启动前通过异步锁原子占位，`IN_FLIGHT/FAILED/CANCELLED/DENIED`
  都计入尝试；RunEvent Sink 使用 ContextVar token 绑定和精确恢复，避免并发 Run 串写；
- 只有调用方显式提供版本化价格表且所有模型调用 Token 完整、价格版本一致时，才计算
  `estimated_cost_usd`；缺值返回 `None`，不猜测。

真实边界：HMAC 只用于本次 Gateway 实例内的关联/指纹，不是匿名化；成本是估算，不是
供应商账单；`FULL_REVIEW` Tool 事件已可由既有 Trace API 查询，但所有工作流尚未共享
同一模型写入器，也没有完整 OTel backend、跨服务 trace/span 或生产监控平台。
