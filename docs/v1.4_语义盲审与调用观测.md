## 1. 本版解决什么问题

v1.3 已经把检索命中、引用集合、确定性词面/数值匹配和业务拒答分开评测，但仍有三个
工程缺口：失败幂等重放只返回泛化错误；Citation-set 一致不能证明 Claim 被证据语义
支持；完整预审中的 Tool 调用缺少统一、可查询的脱敏记录。v1.4 对应补齐：

1. **失败可解释重放**：新请求使用 `grounded_qa_request_v2`；失败 Run 只从唯一、最后、
   与租户/案件/状态转换一致的终态事件恢复固定错误枚举。v1.3 已完成 Run 仍可在旧 Hash
   与原始 `RUN_CREATED` 契约同时匹配时兼容重放；旧失败或疑似降级伪装一律拒绝。请求
   取消时不吞 `CancelledError`；`shield` 保护 best-effort 失败收口，但没有应用层 timeout。
   DB 可用时通常以 `QA_CALL_CANCELLED` 终结 Run；若 DB 同时不可用，清理失败不覆盖原取消，
   持久收口仍依赖未来的 lease/reconciler。
2. **受控人工语义蕴含协议**：从正式 prediction 与 gold-free raw checkpoint 构建
   Claim-Evidence Source，再为两名隔离真人生成独立随机顺序的评审包和空白 worksheet；
   完整 worksheet 经显式隔离声明编译为 submission。两人不形成严格共识的项目再进入
   第三名隔离真人的盲化裁决包，最后由 `--require-complete` 做正式完成门禁。生成、评审和
   裁决全程都不调用模型，也不让同一个生成模型给自己打分。
3. **统一调用信封**：Model/Tool 共用只含身份、状态、时间、Hash、Token 和安全错误码的
   `InvocationEnvelope`。`FULL_REVIEW` Tool 通过 best-effort sink 尝试写入现有
   `run_events`，成功时沿用 Run、tenant、case 和连续 sequence；普通 sink/DB 失败可能导致
   对应事件缺失。Model 侧提供 `adapt_model_invocation_trace()` 显式转换 helper，但生产 QA
   持久化仍直接写 legacy `MODEL_INVOCATION_*`，尚未自动接入统一 envelope/writer。

## 3. 受控评审执行步骤

### 3.1 如需重新构建 Source

```powershell
uv run python scripts/build_entailment_source.py `
  --prediction evaluation/predictions/answer_eval_v1_c4289a1_20260810T125041Z.json `
  --raw-checkpoint evaluation/predictions/answer_eval_v1_c4289a1_20260810T125041Z.json.raw.checkpoint.json `
  --evidence-checkpoint evaluation/predictions/answer_eval_v1_c9decbc_20260809T1442Z.json.raw.checkpoint.json `
  --source-id answer-eval-v1-c4289a1-semantic-source-v1 `
  --created-at 2026-08-12T14:33:02.696624Z `
  --output evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json
```

`--created-at` 必须带时区；固定该值可逐位复现上面的 Source SHA。省略时使用当前 UTC，适合
生成新的评审批次，但产物时间戳与文件 Hash 会相应变化。所有输入/输出路径会做底层文件
同一性检查，硬链接别名也会 fail closed；已存在输出默认不覆盖，必须显式传 `--overwrite`。

raw checkpoint 可能包含完整合成证据正文，Source 又含管理员解盲所需的 question/claim ID；
二者均由 `.gitignore` 排除。Git 只归档构建/校验代码、无真实映射的 Schema 模板，以及
Source 的 SHA、Claim/Evidence 数和输入 Hash 证明，不归档正式 Source 本体。`packages/`、
`submissions/`、`reports/` 和 `evaluation/semantic/*.json` 也默认忽略，避免操作者把评审
中间产物误写到公开路径后提交。真人身份与高熵伪名的对应关系还应单独保存在私有 roster
中；Source、review/adjudication mapping、roster、submission 和报告都由评测管理员受控
分发，不能进入 Git。

### 3.2 准备三套互不复用的高熵伪名

为两名评审员和一名候选裁决员分别生成 **22–128 位、URL-safe、不可猜测且互不复用**的
高熵伪名。下文使用环境变量，不在文档或命令历史中写固定示例值：

```powershell
$reviewer1 = $env:CREDITLENS_REVIEWER_1_ID
$reviewer2 = $env:CREDITLENS_REVIEWER_2_ID
$adjudicator = $env:CREDITLENS_ADJUDICATOR_ID
$reviewPackageGeneratedAt = $env:CREDITLENS_REVIEW_PACKAGE_GENERATED_AT
$adjudicationPackageGeneratedAt = $env:CREDITLENS_ADJUDICATION_PACKAGE_GENERATED_AT
```

真人姓名、联系方式与伪名的对应关系只写入管理员私有 roster。代码只校验伪名为 22–128 位
URL-safe 字符；CSPRNG 高熵生成、不复用、不使用真实姓名/邮箱/可预测工号，以及不同物理真人
之间的分配，均由管理员操作协议、隔离账号和人工监督保证。评审员之间、评审员与裁决员之间
不得共享伪名或 worksheet。`CREDITLENS_REVIEW_PACKAGE_GENERATED_AT` 必须是带时区的 ISO 8601 时间；同一批次
两套 review package 使用同一个已冻结值，但该时间值不包含或暗示任何 reviewer 身份。
`CREDITLENS_ADJUDICATION_PACKAGE_GENERATED_AT` 同样必须带时区，并作为裁决批次的独立冻结值。

### 3.3 为两名评审员分别生成 package 与空白 worksheet

```powershell
uv run python scripts/build_entailment_review_package.py `
  --source evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json `
  --reviewer-id $reviewer1 --ordering-seed $env:CREDITLENS_REVIEWER_1_SEED `
  --generated-at $reviewPackageGeneratedAt `
  --output evaluation/semantic/packages/reviewer-1.package.json `
  --mapping-output evaluation/semantic/private/reviewer-1.mapping.json

uv run python scripts/build_entailment_review_worksheet.py `
  --package evaluation/semantic/packages/reviewer-1.package.json `
  --reviewer-id $reviewer1 `
  --output evaluation/semantic/packages/reviewer-1.worksheet.json

uv run python scripts/build_entailment_review_package.py `
  --source evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json `
  --reviewer-id $reviewer2 --ordering-seed $env:CREDITLENS_REVIEWER_2_SEED `
  --generated-at $reviewPackageGeneratedAt `
  --output evaluation/semantic/packages/reviewer-2.package.json `
  --mapping-output evaluation/semantic/private/reviewer-2.mapping.json

uv run python scripts/build_entailment_review_worksheet.py `
  --package evaluation/semantic/packages/reviewer-2.package.json `
  --reviewer-id $reviewer2 `
  --output evaluation/semantic/packages/reviewer-2.worksheet.json
```

`--generated-at` 省略时会取当前 UTC，产物字节随运行改变；正式批次必须显式传入上面的共同
aware 时间。对任一评审员，在 Source 精确字节、该评审员私有高熵伪名、ordering seed 和
`generated-at` 均保持不变时，package 与 mapping 可以逐字节复现。两名评审员使用各自固定
seed，不能为了复现而公开或写死 reviewer pseudonym。

只把每个人对应的 `package + worksheet + 已分配伪名` 交给该评审员；Source、仓库 gold、
另一人的材料和 `private/` 中的 question/claim mapping 都不能开放。评审账号或分发环境必须
与代码/数据仓库隔离；否则仅靠随机排序不能形成有效的受控盲化。worksheet 仅含 ordinal、
blind item ID、待填 decision/rationale 以及输入 Hash，不含 question/claim ID、gold 或 Source
mapping。

两名隔离真人逐项填写 worksheet。评审标签为
`ENTAILED / CONTRADICTED / NOT_ENOUGH_INFO`；无法判断可标 `SKIP`，证据互相冲突可标
`CONFLICT`，后二者必须写理由，且不冒充语义标签。

### 3.4 由两名真人各自编译完整 submission

每名评审员只在所有项目填写完毕后运行编译命令；以下五个 attestation 参数只能在本人确认
内容属实时传入：

```powershell
uv run python scripts/compile_entailment_submission.py `
  --package evaluation/semantic/packages/reviewer-1.package.json `
  --worksheet evaluation/semantic/packages/reviewer-1.worksheet.json `
  --reviewer-id $reviewer1 `
  --attest-human `
  --attest-no-model-assistance `
  --attest-no-repo-or-gold-access `
  --attest-no-source-or-mapping-access `
  --attest-no-reviewer-coordination `
  --output evaluation/semantic/submissions/reviewer-1.submission.json

uv run python scripts/compile_entailment_submission.py `
  --package evaluation/semantic/packages/reviewer-2.package.json `
  --worksheet evaluation/semantic/packages/reviewer-2.worksheet.json `
  --reviewer-id $reviewer2 `
  --attest-human `
  --attest-no-model-assistance `
  --attest-no-repo-or-gold-access `
  --attest-no-source-or-mapping-access `
  --attest-no-reviewer-coordination `
  --output evaluation/semantic/submissions/reviewer-2.submission.json
```

这些 attestation 是评审员的**自我声明，不是技术证明**。CLI 会强制声明齐全、伪名 Hash、
package 精确字节 Hash、项目全集/顺序和时间链一致，但无法从技术上证明操作者确为真人或从未
访问模型、仓库、gold、Source、mapping 或另一名评审员。

### 3.5 若有非共识项，生成公开裁决包与私有 mapping

严格共识仅指同一 Claim 收到两个人相同的三个语义标签之一。两人语义标签不一致，或任一人
给出 `SKIP/CONFLICT`，都必须进入裁决。若所有 Claim 均形成严格共识，则无需创建裁决包，
可直接执行 3.8 的最终门禁。

```powershell
uv run python scripts/build_entailment_adjudication_package.py `
  --source evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json `
  --package evaluation/semantic/packages/reviewer-1.package.json `
  --mapping evaluation/semantic/private/reviewer-1.mapping.json `
  --submission evaluation/semantic/submissions/reviewer-1.submission.json `
  --package evaluation/semantic/packages/reviewer-2.package.json `
  --mapping evaluation/semantic/private/reviewer-2.mapping.json `
  --submission evaluation/semantic/submissions/reviewer-2.submission.json `
  --adjudicator-id $adjudicator `
  --ordering-seed $env:CREDITLENS_ADJUDICATION_SEED `
  --generated-at $adjudicationPackageGeneratedAt `
  --output evaluation/semantic/packages/adjudication.package.json `
  --mapping-output evaluation/semantic/private/adjudication.mapping.json
```

公开 `adjudication.package.json` 只含争议项的盲 ID、Claim/Evidence 和匿名随机顺序的先前
decision，不含 rationale、`question_id`、`claim_id`、reviewer/adjudicator 原始伪名、真人
身份或 gold。解盲 ID、review bundle Hash 与 Source 绑定只在私有 mapping 中。裁决 mapping、
roster、两份原始 submission 均不得交给裁决员或进入 Git。固定 Source 与两套 review bundle
精确字节、私有 adjudicator pseudonym、ordering seed 和 `generated-at` 可逐字节复现裁决
package/mapping，但不得为此公开或写死裁决员伪名。裁决 `generated-at` 还必须不早于两份
review submission 的 `submitted_at`，否则时间链校验 fail closed。

### 3.6 为第三名隔离真人生成并填写裁决 worksheet

```powershell
uv run python scripts/build_entailment_adjudication_worksheet.py `
  --package evaluation/semantic/packages/adjudication.package.json `
  --adjudicator-id $adjudicator `
  --output evaluation/semantic/packages/adjudication.worksheet.json
```

第三名真人只能接收 `adjudication package + worksheet + 已分配裁决伪名`，不得访问仓库、
gold、Source、私有 mapping、原始 reviewer submission 或评审员身份。裁决员逐项选择
`ENTAILED / CONTRADICTED / NOT_ENOUGH_INFO / EXCLUDE` 并填写 rationale；`EXCLUDE` 表示该
Claim 无法形成可用的最终语义标签，不能把它计为已支持。

### 3.8 执行正式完成门禁并生成最终报告

存在争议项时使用完整命令：

```powershell
uv run python scripts/score_entailment_review.py `
  --source evaluation/semantic/private/answer_eval_v1_c4289a1_entailment_source_v1.json `
  --package evaluation/semantic/packages/reviewer-1.package.json `
  --mapping evaluation/semantic/private/reviewer-1.mapping.json `
  --submission evaluation/semantic/submissions/reviewer-1.submission.json `
  --package evaluation/semantic/packages/reviewer-2.package.json `
  --mapping evaluation/semantic/private/reviewer-2.mapping.json `
  --submission evaluation/semantic/submissions/reviewer-2.submission.json `
  --adjudication-package evaluation/semantic/packages/adjudication.package.json `
  --adjudication-mapping evaluation/semantic/private/adjudication.mapping.json `
  --adjudication-submission evaluation/semantic/submissions/adjudication.submission.json `
  --require-complete `
  --output evaluation/semantic/reports/entailment_report_v1.json
```

若没有争议项，则省略三个 `--adjudication-*` 参数，仍必须保留 `--require-complete`。三个
裁决参数是 all-or-none；任何 package/mapping/submission 字节漂移、伪名不匹配、过期输入、
时间倒序、缺项或重复项都会 fail closed。

对当前 **41 Claim** 的代码正式完成条件是：恰好两套 package、两个不同 reviewer 伪名、总计
**82 个 rating** 且每个 Claim 恰好两票；所有非严格共识项都由一个不同于两个 reviewer
伪名的 adjudicator 伪名裁决为最终语义标签或 `EXCLUDE`；最终每个 Claim 均已获得标签或被
显式排除。操作协议要求两名隔离评审真人和必要时的第三名隔离裁决真人，但这由私有 roster、
隔离账号和人工监督保障；代码只能校验伪名不同、材料完备及 HUMAN 自我声明，不能证明三个
不同物理真人。任一技术条件不满足时，`formal_completion=INCOMPLETE`，`--require-complete`
会在写出/覆盖报告前失败。

报告区分原始 reviewer 的微/宏标签率、覆盖率、一致性，以及仅由双人严格共识或裁决形成的
`final_label_rates`。其中 final entailed rate 的分母是已有最终语义标签的 Claim（显式
`EXCLUDE` 不进入该分母），并应与 `final_label_coverage/excluded_claims` 一起披露。它只是
**Claim 被所给 Evidence 语义支持的代理指标**，不是答案正确率，也不覆盖遗漏要点、拒答质量
或完整业务决策正确性。

### 3.9 文件安全与当前状态

所有构建/编译/评分 CLI 默认禁止覆盖，也拒绝 output 与任一 input 同路径、硬链接别名、
符号链接或 reparse point；只有显式 `--overwrite` 才原子替换常规文件。公开包也仍属于受控
评测材料，不能因此上传公开仓库；private mapping/roster/Source/submission/report 更必须保持
私有且不进入 Git。

**当前已在私有忽略目录生成两套各 41 项的 package + blank worksheet + mapping kit，但没有
任何真人填写的 label、review submission、adjudication package/submission 或正式语义
分数。** `formal-readiness-incomplete.json` 仅诊断 `INCOMPLETE` 与收到 0/82 rating，不是正式
语义报告或分数，不能引用其中的零值 label rate。Source、kit 和 readiness 就绪不等于
`semantic_entailment_evaluated=true`；当前不能声称 Semantic Entailment 结果，更不能把 v1.3
Citation F1 或未来 final entailed rate 称为 Faithfulness。

## 4. Invocation Envelope 与边界

统一信封支持：

- `MODEL / TOOL`、`SUCCESS / FAILED / DENIED / CANCELLED`；
- provider/model/tool/version、actor、task、aware 时间、monotonic latency；
- Prompt/Request/Response 指纹、Token、尝试次数与固定错误码；
- Tool 输入输出使用实例密钥 HMAC-SHA256 和带类型的规范化；不可规范化时只记录安全
  错误码，绝不把观测失败改成工具业务失败；
- 同一 task 的预算在工具启动前通过异步锁原子占位，`IN_FLIGHT/FAILED/CANCELLED/DENIED`
  都计入尝试；RunEvent Sink 使用 ContextVar token 绑定和精确恢复，避免并发 Run 串写；
- RunEvent Sink 是 best-effort：普通 sink/DB 失败不反转工具业务结果，但对应持久事件可能
  缺失，仅内存 record 增加 `observability_error_codes`；sink 收到取消时继续传播；
- 只有调用方显式提供版本化价格表且所有模型调用 Token 完整、价格版本一致时，才计算
  `estimated_cost_usd`；缺值返回 `None`，不猜测。

真实边界：HMAC 只用于本次 Gateway 实例内的关联/指纹，不是匿名化；成本是估算，不是
供应商账单；Trace API 只能查询成功持久化的 `FULL_REVIEW` Tool 事件，当前没有 durable
telemetry outbox/retry，不能保证每次调用都有 RunEvent。所有工作流也尚未共享同一模型
写入器；显式 Model adapter helper 未自动接入生产 QA 持久化路径。当前没有完整 OTel
backend、跨服务 trace/span 或生产监控平台。
