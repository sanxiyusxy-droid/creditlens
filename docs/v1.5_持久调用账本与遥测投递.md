## 1. 为什么要做这一版

v1.4.0 已把 Model/Tool 调用统一为脱敏 Invocation Envelope，但生产接线仍存在两个缺口：

1. FULL_REVIEW Tool 终态只 best-effort 写入 `run_events`，数据库或 sink 短暂失败时可能
   丢失调用事实；
2. Grounded QA Model 仍使用 legacy `MODEL_INVOCATION_*` 事件，统一 Envelope 只是显式
   adapter，不能用一个查询面稳定检查 Model 与 Tool 调用。

v1.5.0 的目标不是一次性搭建完整可观测平台，而是先建立一个可信的最小地基：

- 每个**已接线的结构化 Model 调用**和每个 ToolGateway 终态都形成
  `InvocationEnvelope v2`；
- 调用事实与投递意图先在 PostgreSQL 同一事务中持久化，再由 Worker 异步投递；
- Trace API 不盲信 JSON，查询前复核 Envelope、Hash、列投影和租户/案件/Run 绑定；
- 投递失败可重试、可回收、可进入死信，并明确暴露 Trace 是否完整；
- 继续坚持脱敏、最小权限、RLS 与 fail-closed，不把“有日志”误写成“完整分布式追踪”。

## 2. 范围与非目标

### 2.1 本版范围

- `InvocationEnvelope` 契约升级为 `invocation_v2`；
- 新增追加写事实表 `invocation_records`；
- 新增可靠投递表 `telemetry_outbox`；
- Grounded QA 和 Policy Agent 的已接线 structured Model 调用写入 v2 账本；
- ToolGateway 的 `SUCCESS / FAILED / DENIED / CANCELLED` 四类终态写入 v2 账本；
- Model/Tool 调用采用短审计事务，`invocation_records` 与 `telemetry_outbox` 同事务提交；
- Outbox Worker 支持领取、租约、过期回收、指数退避、最大次数和 `DEAD`；
- `GET /runs/{id}/trace` 返回调用明细、完整性复核结果与投递汇总；
- PostgreSQL RLS、父记录绑定和列级权限覆盖两张新表。

### 2.2 明确不在本版

- 不提供 exactly-once 投递；
- 不接 OpenTelemetry、Prometheus、Grafana 或生产 Dashboard；
- 不为 v1.4 及更早 Run 回填 `invocation_records`；
- 不自动覆盖 `generate_text` 等自由文本 Model 调用；
- 不提供业务 Run 的 lease、heartbeat、reconciler 或持久任务队列；
- 不保证数据库事务提交前的进程崩溃、断电或数据库不可用也能留下调用记录。

## 3. 总体架构

```text
Grounded QA structured Model ─┐
Policy structured Model ──────┼─> InvocationEnvelope v2
ToolGateway 四类终态 ──────────┘              │
                                               │ 独立短审计事务
                         ┌─────────────────────┴─────────────────────┐
                         │                                           │
                 invocation_records                         telemetry_outbox
                 追加写调用事实                              PENDING 投递意图
                         └─────────────────────┬─────────────────────┘
                                               │ 同事务提交
                          ┌────────────────────┴────────────────────┐
                          │                                         │
                 GET /runs/{id}/trace                    TelemetryOutboxWorker
              校验 payload/hash/投影/绑定          lease + reclaim + backoff + DEAD
                                                                    │
                                                       专用幂等 Telemetry Exporter
```

关键顺序是“**先落可信事实，再异步导出**”。业务路径不需要等待外部观测系统，但调用账本
写入失败时，已接线的银行审查路径会 fail closed，避免返回一个没有最小审计事实的正常结果。

## 4. InvocationEnvelope v2

`InvocationEnvelope` 是 Model 与 Tool 的统一脱敏终态契约，主要字段包括：

- 身份：`invocation_id`、`contract_version=invocation_v2`、`kind`、`name`；
- 归属：`actor_role`、`task_id`，数据库行另绑定 `tenant_id/case_id/run_id`；
- 版本：`provider`、`model`、`version`；
- 时间：`started_at`、`ended_at`、`latency_ms`、`time_quality`；
- 结果：`SUCCESS / FAILED / DENIED / CANCELLED` 与稳定 `error_code`；
- 脱敏指纹：请求/响应/Prompt 指纹、规范化版本、HMAC key version；
- Model 专属：Token、尝试次数、显式价格版本下的成本估算、安全 Schema 诊断；
- 观测自身异常：有界的 `observability_error_codes`。

Tool 请求参数和结果使用实例密钥 HMAC 指纹，能够做同实例内的关联和完整性检查，但它
**不是匿名化**。账本不保存原始 Prompt、工具参数、模型原文、Pydantic error message、
traceback、数据库异常文本或供应商错误正文。成本只在 Token 完整且命中显式版本化价格表时
估算；缺值保持缺值，不猜测，也不冒充供应商账单。

## 5. 事务、幂等与持久化边界

### 5.1 同事务双写

`InvocationWriter` 在一个数据库事务内同时插入：

1. `invocation_records`：不可变的调用终态事实；
2. `telemetry_outbox`：主题为 `INVOCATION_TERMINATED` 的投递意图。

任一写入或校验失败都会回滚该短事务，不会出现“有事实、没投递意图”或“有投递意图、没
事实”的正常提交状态。持久性从事务提交成功后开始，不延伸到提交前。

API 的 Grounded QA 与 FULL_REVIEW 生产接线路径使用独立短审计事务，避免调用账本长期
挂在 Multi-Agent 工作流事务中；同一个短事务内仍保证 record/outbox 原子提交。轻量协议测试
可显式复用调用方 Session，但不代表生产运行方式。

### 5.2 Invocation UUID 幂等

- 新 `invocation_id`：写入一条事实和一条 Outbox；
- 同 UUID、同 Envelope Hash、同 tenant/case/run 与同 topic：返回已有记录，不重复插入；
- 同 UUID 但内容、Hash、列投影、父绑定或 Outbox 关系不一致：返回
  `INVOCATION_ID_CONFLICT` 或 `INVOCATION_AUDIT_PERSIST_FAILED`，fail closed。

UUID 是导出端的 `idempotency_key`。由于 Worker 采用 at-least-once，外部 Exporter 必须按
该 key 去重；本系统不能替外部系统宣称 exactly-once。

## 6. 运行时接线

### 6.1 Structured Model

- Grounded QA 使用 traced structured generation；成功、Provider 失败、Schema 修复耗尽等
  已产生的终态 Trace 会进入 v2 账本；
- Policy Agent 在 Provider 支持 traced structured generation 时写 v2 账本；
- v2 写入取代对应 legacy Model RunEvent，不做同一调用双写；
- `generate_text` 等自由文本调用仍未接入，不能声称“所有 LLM 调用均已覆盖”。

### 6.2 ToolGateway

ToolGateway 在调用预算和 Allowlist 约束下，为四类终态生成同一契约：

- `SUCCESS`：工具成功，并记录响应 HMAC 指纹；
- `FAILED`：工具异常，只记录稳定安全错误码；
- `DENIED`：Allowlist 或调用预算拒绝，仍形成审计事实；
- `CANCELLED`：调用协程被取消，尝试形成取消终态事实。

生产 FULL_REVIEW 绑定 durable v2 sink，并设置 `fail_closed=True`；v2 sink 优先于 legacy
RunEvent sink，避免同一 Tool 调用重复写两种事实源。

### 6.3 取消语义

取消是控制流，不可吞掉。v1.5 的 Tool 与 QA 在取消路径把持久化放进被 `shield` 的独立
任务，并通过 `invocation_cancel_persist_timeout_seconds` 只限制**调用方同步等待该任务的
时间**。这个超时不是数据库 statement timeout、transaction deadline 或 DB deadline；
调用方等待超时并
继续传播原始 `CancelledError` 后，被 shield 的底层事务仍可能稍后提交，也可能稍后失败。

因此本版的正确口径是“调用方等待有上限，取消不被观测清理改写，底层持久化 best-effort
继续”，不是“数据库操作有硬超时”或“任何取消都保证持久化”。v1.4 的历史取消收口只有
`shield`，没有这项调用方等待 timeout。

## 7. Telemetry Outbox 状态机

```text
PENDING --领取并增加 attempts--> PROCESSING --导出成功--> DELIVERED
   ^                                 │
   │                                 ├─失败且未达上限--退避--> PENDING
   │                                 └─失败且达到上限────────> DEAD
   │
   └──── PROCESSING 租约过期、未达上限时 reclaim

PROCESSING 租约过期且 attempts 已达上限 ---------------------> DEAD
```

Worker 的关键行为：

- PostgreSQL 用 `FOR UPDATE SKIP LOCKED` 领取，降低多 Worker 重复抢同一行；
- 领取时写入 `locked_at/locked_until` 并增加 `attempts`；
- Worker 崩溃或 Exporter 协程取消后，`PROCESSING` 会在租约过期后被回收；
- 普通失败按指数退避重新变为 `PENDING`，退避有最大值；
- 达到 `max_attempts` 后进入 `DEAD`；取消留下的过期 lease 若已耗尽次数，也会在下一次
  扫描中直接转 `DEAD`，不会无限重试；
- 导出成功只在仍持有对应 lease 时写 `DELIVERED`；丢失 lease 时不覆盖新 Worker 的状态。

发送给 Exporter 的 `TelemetryDelivery` 显式携带
`invocation_id/tenant_id/case_id/run_id/topic`，不允许只靠 Envelope 猜所属范围。

### 7.1 为什么是 at-least-once

Exporter 已接收数据但 Worker 在提交 `DELIVERED` 前崩溃时，该行会在租约到期后再次投递。
这正是 at-least-once 的典型重复窗口。用 Invocation UUID 做幂等键可以让合格 Exporter 去重，
但不能把跨数据库、跨网络的两个提交包装成 exactly-once。

## 8. Trace API 的完整性判定

`GET /runs/{id}/trace` 保留已有 `run_events`，并新增 `invocations`、`integrity` 和
`delivery`。每条 Invocation 在返回前复核：

1. `payload_redacted` 能按 `InvocationEnvelope v2` 重新解析；
2. 由 Envelope 重建的公开投影与持久 JSON 完全一致；
3. Envelope 字段与关系表投影列完全一致；
4. Envelope Hash 与 `payload_sha256` 使用常量时间比较一致；
5. Invocation 与当前 `review_runs` 的 tenant/case/run 绑定一致；
6. 对存在的 Outbox 复核 tenant/case/run/invocation/topic 绑定；合法 InvocationRecord 没有
   Outbox 时单独分类为 `MISSING`，而不是把其 Envelope 误判为 `INVALID`。

payload、Hash、投影或绑定校验失败时 API 不回显可疑的持久 payload，只返回稳定的完整性
错误和 `delivery.status=INVALID`；合法 InvocationRecord 仅缺 Outbox 时则返回
`delivery.status=MISSING`。

投递汇总状态：

- `COMPLETE`：**当前持久 Invocation 集合**全部通过完整性校验，且各自 Outbox
  均为 `DELIVERED`；它不证明所有实际发生的调用都已成功入账；
- `PENDING`：记录完整，但至少一条仍为 `PENDING/PROCESSING`；
- `DEGRADED`：存在 `DEAD/MISSING/INVALID` 或孤立 Outbox；其中 `MISSING` 表示一条本身
  合法的 InvocationRecord 没有对应 Outbox，`INVALID` 表示 payload、Hash、关系列投影或
  tenant/case/run/invocation/topic 绑定损坏；
- `EMPTY`：Run 声明使用 v2，但当前没有持久 Invocation。它既可能是合法的零调用 Run，
  也可能是数据库提交前故障造成的未入账；当前没有 expected-invocation set、预留记录或预期
  数量，无法区分这两种情况，因此不能由 `EMPTY` 证明完整或缺失；
- `LEGACY_UNAVAILABLE`：历史 Run 未声明 v2 且没有新账本数据，不伪造成 `EMPTY` 或
  `COMPLETE`。

响应同时提供各底层状态计数与 `complete` 布尔值，便于 UI、审计脚本或未来监控系统
使用。当前 `complete=true` 只描述“查询到的持久集合有效且均已投递”；没有调用预期集合时，
它不具备调用覆盖率证明能力。Trace 完整性也不等价于业务答案正确或外部平台已经构建完整
span tree。

## 9. PostgreSQL 权限与 RLS

迁移头升级为 `0009_invocation_telemetry`。两张新表启用并强制 RLS：

- `invocation_records` 必须满足当前 tenant、案件 Membership，以及对应
  `review_runs(id, tenant_id, case_id)` 父绑定；
- `telemetry_outbox` 除上述 Run 绑定外，还必须绑定同一
  `invocation_records(invocation_id, tenant_id, case_id, run_id)`；
- 业务角色对 `invocation_records` 只有 `SELECT/INSERT`，没有 `UPDATE/DELETE`；
- 业务角色不能删除 Outbox，也不能修改其 tenant/case/run/invocation/topic；列级授权只开放
  status、attempts、available/lock、稳定错误码和 delivered/dead 时间等投递生命周期列；
- `review_runs` 的 tenant/case/input snapshot 等归属列不可修改，只保留状态、版本、Manifest
  和完成时间所需的列级更新权限。

数据库外键、RLS `WITH CHECK` 和列级权限是三道互补防线，但当前 Outbox 生命周期列的
`UPDATE` 权限由 API 与内置 Worker 共用的 `creditlens_app` 角色持有，数据库不能区分
是哪一方发起更新。专用生产 Worker role 尚未实现；不能把普通 API 的单租户 Membership
会话误当成跨租户后台服务身份。

## 10. Worker 配置与部署

默认值遵循安全关闭：

```dotenv
INVOCATION_CANCEL_PERSIST_TIMEOUT_SECONDS=2.0
TELEMETRY_OUTBOX_WORKER_ENABLED=false
TELEMETRY_EXPORTER_BACKEND=disabled
TELEMETRY_EXPORT_BATCH_SIZE=32
TELEMETRY_EXPORT_POLL_SECONDS=2.0
TELEMETRY_EXPORT_MAX_ATTEMPTS=5
TELEMETRY_EXPORT_LEASE_SECONDS=60
TELEMETRY_EXPORT_BASE_BACKOFF_SECONDS=5
TELEMETRY_EXPORT_MAX_BACKOFF_SECONDS=300
```

`INVOCATION_CANCEL_PERSIST_TIMEOUT_SECONDS` 是调用方等待上限，不会向数据库驱动施加硬
deadline，也不会在超时后取消被 shield 的持久化任务。

内置 `NoopTelemetryExporter` **不会假装导出成功**，而是抛出
`TELEMETRY_EXPORTER_NOT_CONFIGURED`，最终按重试策略进入 `DEAD`。API 内置 Worker 仅允许
在 `local/development/dev/test` 环境中显式选择 `noop`，并固定到演示 tenant/user shard，
用于验证生命周期与失败路径；生产环境不能启用这条内置路径。

生产部署必须提供：

1. 实际的幂等 Exporter；
2. 专用 Worker 进程；
3. 新增并部署专用 service role 或按 tenant 分片的身份；当前仓库尚未实现专用生产
   Worker role；
4. 外部系统对 `invocation_id` 的幂等约束；
5. 对 `PENDING/PROCESSING/DEAD` 积压的监控和人工处置流程。

## 11. 故障语义速查

| 故障点 | 系统行为 | 能否声称有持久记录 |
|---|---|---|
| record/outbox 任一插入失败 | 同一短事务回滚，已接线正常业务路径 fail closed | 否 |
| 数据库提交成功，Exporter 暂时失败 | 退避重试，未达上限时回到 `PENDING` | 是 |
| Worker/Exporter 在处理期崩溃或取消 | 先保留 `PROCESSING`，租约过期后回收或转 `DEAD` | 是 |
| Exporter 成功、`DELIVERED` 提交前崩溃 | 可能再次投递，靠 UUID 幂等去重 | 是，但可能重复投递 |
| 达到最大投递次数 | `DEAD`，Trace 为 `DEGRADED` | 是，但导出不完整 |
| 合法 InvocationRecord 的 Outbox 缺失 | 该 Invocation 标为 `MISSING`，Trace 为 `DEGRADED` | 事实行存在，但投递意图缺失 |
| payload/Hash/投影/父绑定被篡改 | 不回显 payload；Trace 为 `DEGRADED/INVALID` | 有行，但不信任内容 |
| Tool/QA 取消且调用方等待超时 | 保留原取消；shield 的事务不会因此被取消，仍可能稍后提交或失败 | 当下不能确定 |
| Tool/QA 取消且 DB 同时不可用 | 保留原取消控制流，best-effort 收口可能失败 | 不保证 |
| 事务提交前进程崩溃 | 没有可承诺的数据库事实 | 否 |
| Trace 返回 `COMPLETE` | 当前可见 Invocation 均有效且已投递 | 不证明未预留/未入账的实际调用不存在 |

## 13. 诚实边界与后续版本

v1.5.0 解决的是“调用终态事实如何可靠落库、复核和异步投递”，不是整个工作流可靠性：

- `run_events` 仍是业务状态事件源，`invocation_records` 是调用事实查询源，两者职责不同；
- outbox 保证数据库提交后的可重试意图，不保证提交前故障，也不等于 exactly-once；
- 当前没有 OTel span、Prometheus 指标、Grafana Dashboard 或告警闭环；
- 历史 Run 不回填，自由文本 Model 调用未覆盖；
- Multi-Agent 后台执行仍是进程内任务。Run lease、heartbeat、fencing、reconciler、
  Celery/Temporal 类持久队列应在后续版本单独设计，避免把“调用投递可靠性”和“业务工作流
  恢复语义”混成一个未经验证的大改动。

面试时可以将本版概括为：**用 append-only 调用账本 + transactional outbox 把 Model/Tool
终态从 best-effort 日志升级为可复核、可重试、可降级的审计事实；同时明确 at-least-once、
取消和数据库提交前故障的边界。**
